# Deployment Guide

## Render

`render.yaml` in the repo root provisions everything automatically:

1. Push the repo to GitHub/GitLab.
2. In the Render dashboard: **New → Blueprint**, point it at the repo.
   Render reads `render.yaml` and creates the web service (Docker,
   built from `Dockerfile`) plus a managed PostgreSQL database.
3. `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are auto-generated by
   Render (`generateValue: true` in render.yaml). `DATABASE_URL` is
   wired automatically from the provisioned database.
4. Set the remaining env vars in the Render dashboard (Environment tab):
   `CORS_ORIGIN`, `FRONTEND_URL`, and whichever of the payment/SMTP
   vars you're using (see `.env.example`).
5. After the first deploy, run migrations. Render's dashboard has a
   **Shell** tab on the web service — open it and run:
   ```bash
   npm run migrate
   ```
6. Confirm it's live: `curl https://<your-service>.onrender.com/health`

Render sets `PORT` automatically; the app reads it via `src/config/env.js`.

## Koyeb

Koyeb can build directly from the `Dockerfile` or from a pushed image.

**Option A — build from GitHub:**
1. In the Koyeb dashboard: **Create App → GitHub**, select the repo.
   Koyeb detects the `Dockerfile` automatically.
2. Add a **PostgreSQL** database (Koyeb's managed Postgres, or point
   `DATABASE_URL` at any external Postgres instance — Neon, Supabase,
   etc. all work).
3. Set environment variables under the service's **Environment** tab —
   same list as `.env.example`. Generate `JWT_ACCESS_SECRET` /
   `JWT_REFRESH_SECRET` yourself:
   ```bash
   openssl rand -hex 64
   ```
4. Deploy. Once running, run migrations via Koyeb's **one-off job**
   feature (or exec into the running instance if your plan supports it):
   ```bash
   npm run migrate
   ```
5. Confirm: `curl https://<your-app>.koyeb.app/health`

**Option B — push a pre-built image:**
```bash
docker build -t your-registry/adstream-api .
docker push your-registry/adstream-api
```
Then point a Koyeb service at that image instead of building from source.

Koyeb also sets `PORT` automatically — no config changes needed to
support both platforms with the same Dockerfile.

## Post-deploy checklist

- [ ] `GET /health` returns `200`
- [ ] `GET /health/ready` returns `200` (confirms DB connectivity)
- [ ] Migrations applied (`npm run migrate` ran without errors)
- [ ] `CORS_ORIGIN` set to your actual frontend domain(s), not `*`,
      once you have one (dashboard endpoints send credentials/cookies,
      which the `cors` package requires an explicit origin for)
- [ ] At least one payment provider's secret key is set, or deposits/
      withdrawals will fail with a clear "not configured" error
- [ ] SMTP configured (or intentionally left unset — the app logs
      emails instead of sending them when `SMTP_HOST` is empty, which
      is fine for a first deploy but not for real users)
- [ ] The first admin account exists (see below — there's no signup
      flow for this by design)

## Provisioning the first admin account

Admin accounts are deliberately not self-registrable (see
`docs/ARCHITECTURE.md`). After a normal registration as any role,
promote that user directly in the database:

```sql
UPDATE users
SET role_id = (SELECT id FROM roles WHERE name = 'admin')
WHERE email = 'you@example.com';
```

## Webhooks

Once deployed, register these URLs in each payment provider's dashboard:

- Paystack: `https://<your-domain>/api/v1/payments/webhooks/paystack`
- Flutterwave: `https://<your-domain>/api/v1/payments/webhooks/flutterwave`
  (also set `FLUTTERWAVE_WEBHOOK_HASH` to match the value you configure
  in Flutterwave's dashboard — it's compared, not derived)
